# 2026-11-07 可靠性复核与修复

基线版本：`1aacbd1`。本次按审核报告先复现、补回归测试，再修复与部署；未把“存在条件风险”表述为“线上已经发生事故”。

## 复核结果

- 真实 NapCat 默认根列表返回 50 个；显式请求 1000 个时返回 518 个。插件漏传列表数量参数的问题成立。
- 同名同大小新版本复用旧内容、并发下载目标冲突、历史命令重新分派、失败事件被去重吞掉、退出遗漏文件任务、中文长名写盘失败、显式零值无效均已在隔离环境再次复现。
- @ 先于文件下载完成、空聊天缓冲不提供归档入口、下载中临时占用不计入容量均成立。
- HTTP 超时后第二路由调用可由模拟客户端复现，但是否造成线上重复发送取决于服务端行为。另发现 Hermes 基类的纯文本 fallback 也会补发，因此一并处理。
- “只有 30MB”的问题是代码默认值与示例不一致；实际配置显式为 200MB，因此本机原本不受这个默认值影响。

## 修复内容

| 链路 | 修复 |
|---|---|
| 文件枚举 | 根与子目录显式请求最多 10,000 项，递归遍历、目录循环保护；枚举与每轮 50 个/1GiB 下载预算分离，未完成约一分钟后继续扫描 |
| 文件版本 | 身份包含目录和上传者，源修改时间区分版本；兼容旧索引；保存 SHA-256，历史版本保持可查询 |
| 并发下载 | 通知与扫描共用下载任务；默认 2 个下载槽；每个目标使用 UUID、独占 `.part`，按字节裁剪中文名 |
| 消息回补 | 成功分派 ID 持久化七天，历史命令永不执行；首次启用前的旧请求只补群上下文；实时收帧与有序分派分离 |
| 失败重试 | 临时解析或媒体失败释放处理中状态，不误记成功；合并批次的每个消息 ID 统一记录 |
| @ 与下载 | 截取聊天快照，最多等待关联下载 5 秒，不阻塞 WebSocket；超时提示正在下载，新消息不混入旧快照 |
| 文件入口 | 聊天缓冲为空时仍提供已有群文件目录；已清理的路径不再被标成有效附件 |
| 清理和容量 | 继续执行七天清理后再按最旧淘汰至 5GiB；活动下载预留空间，完成后复查；保留版本墓碑防止回扫立刻下载已淘汰版本 |
| 大媒体 | 远程媒体流式下载，实际字节限制、总时间检查、短网络等待和协作停止；普通媒体仍使用 Hermes 自有缓存，不扩大群文件目录淘汰范围 |
| 退出 | 回收接收、回补、扫描、文件下载和批次任务；等待维护线程退出后释放索引锁，避免取消协程后线程仍在修改共享数据 |
| HTTP | 只读请求探测路由，业务错误检查 retcode；写操作结果未知不换路由重试；QQ 不使用基类的再次纯文本补发 |
| 配置/安装 | 明确零值和无效数值；默认单文件 200MiB；安装器增加必要集成检查和真实 import，支持只读 `--verify-only` |

## 保留的边界

1. 持久化表示“成功交给 Hermes 处理器”，不表示模型或工具最终成功。分派与记录之间的突然断电仍有不确定窗口，不承诺外部工具副作用严格只执行一次。
2. 缓存版本判断依赖 NapCat 提供的版本时间等元数据；完全相同元数据但内容被上游悄悄替换时，不能在不重新下载的情况下发现变化。SHA-256 用于下载后完整标识内容。
3. 7 天是最长留存期，容量超限时可提前淘汰。5GiB 针对群文件归档及其活动下载，不包括整个 Hermes 的其他平台缓存；索引有少量额外元数据开销。
4. 下载线程在块间检查退出标志和总时间，并使用短网络等待。停止属于协作式退出，不能宣称 Python 能强制终止任意第三方阻塞线程。
5. 保留原有“只回 @、过滤小小噜、最近 15 条且两小时过期”的配置。首次采用持久化时不会重跑启用前的旧任务。
6. 没有为修复顺便大规模重构整个 adapter。把持久状态、数值校验、流式下载抽到 `reliability.py`，后续结构优化应在回归保障下分批进行。
